## 第六層：citation path 回傳

QAOrchestrator 會從 retrieved chunks 建 citation：

```python
notion_path
page_id
score
```

TelegramQAOrchestrator 再把 citation path 加到回覆最後：

```text
Notion citations:
- path1
- path2
```

這讓使用者可以知道答案來自哪些 Notion path，不是黑盒回答。

---

# 7. 回覆格式怎麼設計？

如果沒有 citations：

```python
return answer
```

如果有 citations：

```python
return f"{answer}\n\nNotion citations:\n{citations}"
```

範例：

```text
RAG means retrieval augmented generation. It retrieves relevant notes first, then asks the LLM to answer based on those notes.

Notion citations:
- AI/RAG Basics
- AI/Agent Workflow
```

這樣設計的好處：

1. 使用者先看到答案
2. citation 放在下面，不干擾閱讀
3. Notion path 比 page id 更適合人類理解
4. Telegram 文字訊息可以直接顯示，不需要複雜 UI

# 8. Workflow / Observability 設計

這一步有兩層 workflow run。

## 第一層：Telegram workflow

由 `TelegramGatewayOrchestrator` 建立：

```python
workflow_type="telegram"
```

它代表這次 Telegram webhook request。

成功時 metadata 會記錄：

```python
handled
command
chat_id
telegram_message_id
source_document_id
change_request_id
source_type
qa_workflow_run_id
insufficient_info
citation_count
```

注意：它記錄的是 `citation_count`，不是完整 citation paths。這是一個 privacy / metadata minimization 的設計決策。

---

## 第二層：QA workflow

由 `QAOrchestrator` 建立：

```python
workflow_type="qa"
```

它代表真正的 QA 子流程。

metadata 會記錄：

```python
operation
query_length
top_k
provider_name
model
request_workflow_id
```

這裡記錄 `query_length`，不是完整 query。這也是避免把使用者問題全文寫進 workflow metadata。

成功後會記錄：

```python
insufficient_info
retrieved_chunk_count
citation_count
provider_name
model
token_input
token_output
```

這對 observability 很重要，因為之後你可以分析：

```text
這次有沒有資訊不足？
抓了幾個 chunks？
用了哪個 provider / model？
token 成本是多少？
```

# 9. 錯誤處理設計

這一步錯誤處理很完整。

## TelegramQAError

`TelegramQAOrchestrator` 如果收到 `QAOrchestratorError`，會轉成：

```python
TelegramQAError
```

但保留：

```python
error_code
message
http_status_code
failure_reason
workflow_run_id
```

這代表 QA 子流程失敗時，錯誤不會被吃掉，也不會失去 QA workflow id。

---

## TelegramGatewayError

`TelegramGatewayOrchestrator` 收到 `TelegramQAError` 後，會：

1. mark Telegram workflow failed
2. 轉成 `TelegramGatewayError`
3. 回到 FastAPI route
4. route 轉成 HTTPException

這讓 API response 可以回傳：

```json
{
  "error_code": "...",
  "message": "...",
  "failure_reason": "...",
  "workflow_run_id": "..."
}
```

也就是錯誤可以被 deterministic mapping，而不是回傳模糊的 500。

---

## Provider failure

如果 provider 沒設定，例如 OpenAI provider not found，`QAOrchestrator` 會 catch：

```python
ProviderNotFoundError
```

並轉成：

```python
PROVIDER_NOT_FOUND
```

如果 LLM provider request failed，會轉成：

```python
LLM_PROVIDER_ERROR
```

如果 LLM 回空字串，會轉成：

```python
LLM_OUTPUT_INVALID
```

這對 production AI 很重要，因為 LLM failure 不能全部混成 unknown error。

# 10. 用到的 library / 技術

## `shlex`

用途：解析 Telegram `/ask` command。

適合原因：

```text
/ask --section "AI Notes/RAG Basics" What is RAG?
```

這種 command 需要支援 quoted strings。`shlex.split()` 可以像 shell 一樣解析引號、空格與 escape。

---

## `dataclasses`

用來定義 lightweight result / parsed command object，例如：

```python
@dataclass
class TelegramQACommandResult:
```

```python
@dataclass
class _ParsedAskCommand:
```

好處是：

1. 比 dict 更清楚
2. 有型別提示
3. 適合在 orchestrator 之間傳遞 structured data
4. 不需要 Pydantic 那麼重

---

## `HTTPStatus`

用來產生清楚的 HTTP status code：

```python
HTTPStatus.BAD_REQUEST
HTTPStatus.INTERNAL_SERVER_ERROR
HTTPStatus.BAD_GATEWAY
```

好處是比直接寫 `400`、`500` 更可讀。

---

## `typing`

包含：

```python
List
Optional
```

讓每個 result、error、method argument 的型別更清楚。

---

## FastAPI

`telegram.py` 使用：

```python
APIRouter
Depends
HTTPException
Request
```

負責 webhook endpoint 與 dependency injection。

---

## SQLAlchemy Session

route 透過：

```python
db_session: Session = Depends(get_db_session)
```

把同一個 DB session 傳給 repositories / services。

---

## ProviderRouter

負責 model/provider 抽象化。

Telegram QA 不直接綁死 OpenAI SDK，而是透過：

```python
ProviderRouter.route(...)
```

這讓未來可以換 Claude、Gemini、Bedrock，而不用改 Telegram command 邏輯。

---

## ToolRegistry

Telegram reply 不是 route 自己送，而是透過：

```python
self._tool_registry.call_tool("telegram_bot", ...)
```

這符合 Harness Engineering 的 tool abstraction：Telegram bot 是一個 tool，不是散落在 business logic 裡的 API call。

# 11. 重要設計決策

## 設計決策 1：Telegram 只做 interface，不複製 QA 邏輯

沒有在 Telegram layer 重新寫一套 RAG / LLM。

正確做法是：

```text
TelegramQAOrchestrator -> QAOrchestrator
```

這避免：

1. QA 邏輯重複
2. production RAG 規則分裂
3. 之後修 QA 時 Telegram 和 API 行為不一致
4. provider / workflow / citation 邏輯重複維護

面試可以說：

> I designed Telegram QA as an adapter over the existing QAOrchestrator instead of duplicating retrieval and LLM logic. This keeps the Telegram interface thin and ensures the same production RAG rules, citation behavior, and error mapping are reused across API and Telegram channels.

---

## 設計決策 2：使用 explicit scope flags

使用：

```text
--page
--section
```

而不是讓模型猜使用者想查哪個頁面。

好處：

1. deterministic
2. 可測試
3. 不需要 LLM parse command
4. 可避免問題文字被誤判成 scope
5. 使用者可以明確控制 retrieval boundary

---

## 設計決策 3：使用 `shlex.split()` 支援 quoted scope

因為 Notion path 很可能有空格：

```text
"AI Notes/RAG Basics"
```

如果用 `.split()` 會壞掉，所以用 `shlex` 讓 command parsing 更像 CLI。

面試可以說：

> I used `shlex.split()` because the Telegram command behaves like a CLI command. It supports quoted section paths, so users can scope QA to Notion paths containing spaces without breaking the parser.

---

## 設計決策 4：資訊不足時不呼叫 LLM 硬答

如果沒有 retrieved chunks 或 citations，直接回 insufficient info。

這是 production AI 非常重要的 guardrail。

面試可以說：

> I intentionally return a deterministic insufficient-information response when retrieval produces no usable citations. This avoids forcing the LLM to answer without grounding and reduces hallucination risk.

---

## 設計決策 5：citation 使用 Notion path

不是只回 page id 或 chunk id。

因為 Telegram 是 user-facing interface，Notion path 比 raw id 更容易理解。

例如：

```text
Notion citations:
- AI/Harness Engineering
- AI/RAG
```

這樣使用者知道答案從哪裡來。

---

## 設計決策 6：metadata 不存完整 query / citation paths

QA workflow metadata 存：

```python
query_length
citation_count
```

Telegram workflow metadata 存：

```python
citation_count
```

而不是完整問題或 citation path。

這是很好的 observability + privacy balance：

```text
需要 debug 的資訊有記錄
但不把使用者內容過度寫進 workflow metadata
```

---

## 設計決策 7：Gateway 與 QA workflow 分開

一次 `/ask` 會有：

```text
telegram workflow_run_id
qa_workflow_run_id
```

這樣可以分辨：

```text
是 Telegram webhook / reply 失敗？
還是 QA retrieval / LLM provider 失敗？
```

對 debug 很有幫助。

---

# 12. 面試可能被問的問題

## Q1. 為什麼不直接在 TelegramGatewayOrchestrator 裡寫 QA logic？

因為 Gateway 的責任是 command dispatch 和 reply delivery，不應該包含 RAG、LLM、citation、provider routing。
如果直接寫在 Gateway，會造成 duplicated business logic，也會讓 `/api/qa` 和 Telegram `/ask` 行為不一致。

比較好的設計是：

```text
TelegramGatewayOrchestrator
    -> TelegramQAOrchestrator
        -> QAOrchestrator
```

這符合 single responsibility 和 layered architecture。

---

## Q2. 你怎麼避免 Telegram `/ask` 回答 hallucination？

主要靠四層：

1. `ProductionChunkRetriever` 先 retrieval production notes
2. scope flags 限制 page / section
3. system prompt 要求 only answer from provided context
4. 沒有 retrieved chunks / citations 時直接 insufficient info，不讓 LLM 硬答

但面試要補一句：

> This does not completely eliminate hallucination, but it reduces the risk by grounding answers in retrieved context and refusing when context is insufficient.

---

## Q3. 為什麼用 `shlex`？

因為 `/ask` command 很像 command line，有 flags 和 free-form question。

例如：

```text
/ask --section "AI Notes/RAG Basics" What is chunking?
```

`shlex.split()` 可以正確處理 quoted strings。
普通 `.split()` 會把 `"AI Notes/RAG Basics"` 切壞。

---

## Q4. 你怎麼處理錯誤？

錯誤會分層轉換：

```text
QAOrchestratorError
   -> TelegramQAError
      -> TelegramGatewayError
         -> HTTPException
```

每一層都保留：

```text
error_code
message
http_status_code
failure_reason
workflow_run_id
```

這樣 API caller 可以知道錯誤原因，workflow run 也可以被標記 failed。

---

## Q5. 為什麼要有 qa_workflow_run_id？

因為 Telegram webhook workflow 和 QA workflow 是兩件事。

Telegram workflow 代表：

```text
收到 Telegram message 並嘗試回覆
```

QA workflow 代表：

```text
執行 RAG + LLM QA
```

如果 Telegram reply failed，但 QA succeeded，要能分辨。
如果 QA failed，但 Telegram gateway 正常收到 webhook，也要能分辨。

---

## Q6. 為什麼 citation 只回 notion path？

因為 Telegram 是人看的介面，Notion path 比 chunk id、page id 更可讀。
而且 QAOrchestrator 內部仍然保留 page id 和 score，因此系統內部可以 debug，使用者端則看到乾淨的 citation path。

---

## Q7. 為什麼不用 LLM 解析 `/ask` 的 scope？

因為 scope parsing 是 deterministic command parsing 問題，不需要用 LLM。

這符合 AI system 的重要原則：

> 能 deterministic 做的事情，就 deterministic 做；只有 fuzzy semantic reasoning 才交給 LLM。

Scope flags 應該由程式解析，回答內容才交給 LLM。

---

## Q8. 這個 Step 跟 Harness Engineering 有什麼關係？

這個 Step 很像一個小型 harness layer：

```text
Interface: Telegram command
Tool: telegram_bot tool
Context: retrieved Notion chunks
Guardrail: insufficient info response
Workflow: telegram workflow + qa workflow
Observability: workflow metadata, citation_count, token usage
Provider abstraction: ProviderRouter
```

也就是把 LLM 包在一個可控、有 scope、有 citation、有 error mapping、有 workflow tracking 的系統裡，而不是直接把 Telegram message 丟給 LLM。

---

# 13. 你可以怎麼用 STAR 故事講這個 Step？

## Situation

原本系統已經有 QA API，可以透過 Production RAG 查 Notion knowledge chunks 並呼叫 LLM 回答問題。但使用者希望可以直接在 Telegram 裡使用 `/ask` 問問題，並且可以限制查詢某個 Notion page 或 section。

## Task

我要新增 Telegram QA command，同時不能複製既有 QA 邏輯，也不能破壞 production RAG rules、citation、workflow tracking 和 deterministic error handling。

## Action

我新增了 `TelegramQAOrchestrator` 作為 Telegram adapter，使用 `shlex.split()` 解析 `/ask` command，支援 `--page` 和 `--section` scope flags。Gateway 只負責 command dispatch 和 telegram reply，真正的 QA 流程仍然重用 `QAOrchestrator`。QAOrchestrator 透過 `ProductionChunkRetriever` retrieval Notion chunks，使用 grounded prompt 呼叫 ProviderRouter，並在回答後附上 Notion path citations。若 retrieval 沒有足夠資料，系統會直接回 deterministic insufficient info answer，而不是讓 LLM 猜。

## Result

最後 `/ask` 可以在 Telegram 上完成 scoped QA，回覆包含 Notion citations。系統保留兩層 workflow observability：Telegram workflow 和 QA workflow。Focused tests 和 full test suite 都通過，包含 Telegram tests、QA/RAG tests、compile check、full suite 112 passed。

---

# 14. 這個 Step 最值得記住的核心

最重要的一句話：

> Step 34 不是把 Telegram 接到 LLM，而是把 Telegram 接到既有 QA Harness。

也就是：

```text
Telegram command
不是直接 call LLM
而是進入：
Gateway -> TelegramQA adapter -> QAOrchestrator -> Production RAG -> ProviderRouter -> citation reply
```

這代表你的系統有：

```text
可重用的 QA workflow
可控的 scope parsing
可追蹤的 workflow run
可驗證的 citation
可預期的 insufficient-info behavior
可替換的 provider routing
```

面試時可以把它包裝成：

> I implemented Telegram `/ask` as an adapter over the existing production QA workflow. The design keeps Telegram-specific parsing and reply formatting separate from core RAG and LLM logic. It supports deterministic scope filtering with `--page` and `--section`, uses production retrieval for Notion chunks, grounds the LLM answer in retrieved context, returns Notion path citations, and records both Telegram-level and QA-level workflow runs for observability and failure diagnosis.
